    夜班工厂里，绝大多数代码由 agent 写。人工审查的注意力是单线程的，所以能并行多少个 agent，取决于它们能不能自己拿出证据证明做对了。

    没有验证闭环，你只能同时盯一两个；有了它，可以放手几十个。下面是我们实际在用的三类测试，以及一条把慢检查当成缺陷的规矩。

    不是所有测试都一样：值得投入的三种

    先避开两个坑：测试一不稳定，agent 就学会“再跑一次”而不是修代码；测试一慢，agent 就少跑，问题就攒到合并前才暴露。

    端到端测试

    单元测试能全绿而功能照样坏，因为 agent 和测试都没理解整件事。端到端测试让 agent 真的打开应用、点一遍、截图、读日志。

    属性测试：不能被打破的约束

    先写一句你认为永远成立的话，再让测试库生成成千上万个输入去推翻它。夜班里最常用的几条：

    • 往返编码：序列化再反序列化，得到原值。
    • 不变量：任何时候账户余额都不能为负。
    • 幂等：同一个迁移跑两遍，结果和跑一遍一样。
    # 每个工单完成前，agent 必须贴出这三行的输出
nightshift check --fast        # ≤ 60s，否则记为缺陷
nightshift check --property    # 1000 个随机输入
nightshift check --e2e --shot  # 截图附在 PR 上

    差分测试：旧系统就是标准答案

    重写一个模块时，把同样的输入同时喂给新旧两套实现，任何不一致都是待解释的差异。旧系统不必完美，它只需要是你已经接受的行为。

    一分钟跑不完就是 bug

    快检查是 agent 每次提交都会跑的东西。它一慢，整条流水线的节拍就跟着慢。我们把超时直接记成工单，和功能缺陷同等优先级。

    检查中位耗时上限状态
    静态检查8 s60 s通过
    属性测试41 s60 s通过
    浏览器截图67 s60 s超时

    好测试，好结果

    验证不是收尾工序，而是让并行成为可能的前提。把规则写进结构——脚本检查、生成的骨架、不变量——而不是写在提示词里求 agent 记住。
